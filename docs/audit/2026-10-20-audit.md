## 5. 架构清晰度评估（对应"是否清晰明了"）

**清晰之处**

1. **分层意图写在代码里**：`confkit/__init__.py` 明确列出 `base → curate → i18n → model → parse → build` 的单向依赖，且确实没有反向导入。
2. **核心层零 GUI 依赖**：`python -m dxvk_toolkit --scan-games` 在没有 PySide6 的机器上可用，CLI 与 GUI 共用同一套领域逻辑。
3. **状态判定的单一入口**：`status_for()` / `_status_tuple()` 把"已装 / 未接管 / 可还原 / 未安装"的语义收在一处，三处分组（网格、列表、排序）共用。
4. **缓存分层有明确失效信号**：版本缓存按 TTL + 元数据合并，检测缓存按目录时间戳，封面按 mtime 比较。
5. **可验证性设计**：`tests/golden/` 的 90 个选项 + 12 份生成文件逐字节比对，是重构时最硬的护栏。

**不清晰之处**

1. **文件即职责**：`bridge.py` 仍超过 1,300 行，新人无法从文件名判断改动该落在哪；`ConfigPage.qml` 1,595 行同理。本轮已把检测与配置存储抽走，但桥接主体仍是"什么都做"。
2. **状态所有权模糊**：`_games` / `_urls` / `_STATUS_CACHE` / `_DETECT_CACHE` / `_INDEX` 五份进程级缓存，失效责任分散在调用方（谁改盘谁记得调 `invalidate()` / `forget_cache_index()`），漏调即读到旧值——A8 就是这类问题；本轮只补了检测缓存的并发写锁，所有权问题仍在。
3. **错误处理策略不统一**：核心层区分"可降级"（封面失败）与"必须报错"（安装失败），但 UI 层大量 `except Exception` 后只写日志，`_refresh_one` 的静默失败正是被这层兜底掩盖的；本轮为 pending 集加了 `on_error` 兜底，但整体策略仍靠约定。
4. **命名与真实行为有偏差**：`statusesReady` 此前无人 emit（本轮改为状态变更通知）；`coverUrlFor` / `metadata` 已在 T36 删除；仍存在「文档描述过、代码没有」的历史残留风险。
5. **入口与打包路径分裂**：`main.py` / `.pyw` / `pyi_launch.py` / `启动.ps1` 四套启动方式；本轮去掉了两处冗余 `sys.path` 操作，但解释器探测逻辑仍在 `启动.ps1` 与 `verify.ps1` 各写一遍。
6. **文档承载了过多"历史状态"**：`TASKS.md` 单行长达数百字、混入验收证据与提交号，作为"现状"阅读成本高；本次已把与代码冲突的部分改写，但结构问题仍在（建议拆 `TASKS.md` 与 `CHANGELOG.md`）。
